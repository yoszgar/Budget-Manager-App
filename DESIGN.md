# Design Rationale

I split the project into five modules (`models`, `validation`, `services`, `storage`, `cli`) so that each one has a single responsibility and can be tested on its own. The key decision is that **all validation lives in one place**, `validation.py`, and is called by `services.add_transaction`. Because of this, a transaction typed in the terminal and a row imported from a CSV file follow exactly the same rules, and the CLI contains no business logic. Invalid input is rejected with a specific message (for example `Row 5: amount must be > 0, got '-5'`) instead of being corrected silently. The trade-off I accepted is that a small typo such as "Food" instead of "food" is rejected rather than fixed automatically, because silent fixes hide bugs and make the data harder to trust. A second trade-off is that Release 1 supports only EUR, so totals can never accidentally mix currencies.
